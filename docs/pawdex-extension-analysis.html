PawDex 제품/확장 분석

보호자 건강기록 앱에서 병원 연계 플랫폼으로 확장하기

현재 앱은 보호자가 반려동물의 증상, 진료, 입퇴원, 일상, 복약, 비용, 파일을 관리하는 개인 건강기록 중심입니다. 다음 단계는 병원과 보호자 사이의 데이터 공유, 예약, 응급 콜, 검사결과 전달, 수의사용 업무 도구를 붙여 “보호자 앱 + 병원용 웹/프로그램 + 커머스” 구조로 키우는 것이 가장 자연스럽습니다.

현재 앱 분석 권한 분리 병원 연계 의사용 창고 커머스 데이터 설계 우선순위

1. 현재 앱 분석

코드 기준으로 확인한 현재 제품은 Next.js 16, Supabase, Toss Payments, OpenAI, PubMed, Kakao Map, Web Push, PWA 구조입니다. 단순 기록장이 아니라 이미 구독/결제, 관리자, AI 분석, 알림, 파일 업로드까지 갖춘 모바일 웹앱에 가깝습니다.

보호자 기록

건강기록이 핵심 자산

  • 증상, 진료, 입퇴원, 일상 기록
  • 반려동물별 기록 필터와 캘린더
  • 진료비/체중 통계
  • 첨부파일, 약, 복약 체크
AI 케어

검색/분석 기능

  • 증상 분석
  • 사진 분석
  • 논문 검색 및 분석
  • 분석 결과 저장
결제

구독 기반 과금

  • Toss Payments 연동
  • 자동결제 빌링키 흐름 구현
  • 결제 이력, 환불, 구독 취소 API
  • 단건 결제는 심사/준비 단계로 보임
관리자

운영 도구

  • 관리자 대시보드
  • 사용자/구독/활동 로그
  • 저장소 사용량
  • 알림 통계, 검색 로그
병원 탐색

오프라인 연결의 시작점

  • Kakao Map 기반 병원 찾기
  • 최근 병원명 저장
  • 기록 입력 시 병원명 연결 가능
현재 빈칸

확장 전 필요한 영역

  • 병원/의사 계정과 권한
  • 보호자-병원 데이터 공유 동의
  • 예약, 검사결과, 진단서 워크플로우
  • 상품 판매자/구매자 페이지
결론: 지금 앱은 보호자 쪽 기록 데이터가 이미 잘 쌓이는 구조입니다. 병원 연계는 새 앱을 따로 만드는 것보다, 현재 기록 데이터를 중심으로 “누가 어떤 범위까지 볼 수 있는가”를 추가하는 방식이 효율적입니다.

2. 보호자와 의사는 이렇게 나누는 것이 좋음

한 화면 안에서 보호자/의사 기능을 섞으면 개인정보, 진료 책임, 병원 운영 흐름이 꼬입니다. 계정 타입과 화면 진입점을 분리하고, 공유는 보호자의 명시 동의로만 열어야 합니다.

역할 주요 목적 볼 수 있는 데이터 할 수 있는 일 추천 화면
보호자 우리 아이 기록, 병원 공유, 예약, 구매 본인 반려동물 전체 기록, 병원이 보낸 검사결과/진단서/처방 안내 기록 작성, 병원 선택, 공유 승인/철회, 예약, 응급 콜, 상품 구매 기존 모바일 앱/PWA
수의사 진료 전후 정보 확인, 검사결과 전달, 예약/응급 대응 보호자가 공유한 반려동물 기록, 병원에서 생성한 문서 환자 타임라인 확인, 문서 업로드, 코멘트, 예약 상태 변경, 담당 수의사 지정 병원용 웹 대시보드
병원 관리자 병원 운영, 직원/상품/예약 관리 병원 소속 수의사, 예약, 병원 문서, 고객 요청 의사 계정 초대, 근무시간/예약 슬롯 설정, 병원 상품/공지 관리 병원 관리자 웹
판매자 상품 등록과 주문 처리 본인 상품, 주문/배송 정보 상품 등록, 상세 페이지 작성, 재고/가격/배송 관리 판매자 센터 웹
PawDex 운영자 전체 운영과 정산/CS 전체 통계, 신고, 결제, 병원/판매자 승인 상태 승인, 정산, 환불, 제재, 공지, 데이터 모니터링 기존 관리자 확장
주의점: 의사가 보호자 기록을 기본으로 전부 보는 구조는 피해야 합니다. “보호자가 병원에 공유 요청 또는 병원이 초대 링크 발급 → 보호자가 동의 → 기간/범위 제한” 구조가 안전합니다.

3. 병원 연계 시스템 구조

처음부터 병원 EMR 전체를 대체하려고 하면 범위가 너무 커집니다. 1차 목표는 병원과 보호자 사이에서 가장 자주 오가는 문서, 예약, 응급 요청, 기록 공유를 처리하는 것입니다.

1

보호자 병원 선택

기존 병원 찾기/최근 병원 기능을 확장해 공식 병원 프로필을 연결합니다.

2

공유 동의

반려동물, 기록 유형, 기간, 첨부파일 공개 여부를 보호자가 선택합니다.

3

의사 확인

담당 수의사는 공유된 타임라인, 증상, 복약, 과거 진료비/검사 파일을 봅니다.

4

진료 후 전달

진단서, 검사결과지, 처방/주의사항, 다음 예약을 병원에서 보호자 앱으로 보냅니다.

5

보호자 기록화

받은 문서는 해당 반려동물의 진료 기록에 자동으로 묶입니다.

MVP 추천

먼저 만들 기능

  • 병원 계정/수의사 계정 생성
  • 보호자 기록 공유 링크 또는 QR 초대
  • 병원 문서 업로드 후 보호자 앱 전송
  • 담당 수의사 선택 예약
  • 예약 확정/변경/취소 알림
2단계

나중에 붙이면 좋은 기능

  • 응급 콜 접수 및 병원 응답 가능 상태 표시
  • 진료 전 문진표 자동 생성
  • 병원별 사후관리 메시지 템플릿
  • 검사결과 OCR/요약
  • 진료 후 필요한 사료/약/용품 추천 구매 연결

4. “의사의 전용 창고”는 별도 제품처럼 설계

수의사들이 쓰는 웹 도구가 적다면, 단순 파일함이 아니라 “진료 중 바로 열 수 있는 환자 자료실 + 병원 문서 발송함”으로 만드는 것이 좋습니다.

환자 타임라인

진료 전 빠른 파악

  • 증상 발생일, 내원일, 입퇴원일
  • 복약 이력과 알림 체크 상태
  • 체중 변화, 진료비, 첨부 파일
문서 보관함

검사결과/진단서 전송

  • PDF, 이미지, 검사 데이터 업로드
  • 보호자 앱으로 전송
  • 문서 열람 여부 확인
템플릿

반복 업무 줄이기

  • 수술 후 주의사항
  • 예방접종 안내
  • 재검 안내
  • 복약 설명 템플릿
예약 보드

담당 수의사 기준 관리

  • 의사별 진료 가능 시간
  • 예약 요청/확정/변경
  • 응급 요청과 일반 예약 분리
프로그램 설치형

병원 PC용 선택지

  • 웹을 먼저 만들고 필요 시 Electron/Tauri로 패키징
  • 스캐너/로컬 파일 드래그 업로드가 중요할 때 유리
  • 초기에는 설치형보다 웹 대시보드가 빠름
중요

EMR 대체는 후순위

  • 차트 전체 작성, 보험/청구, 재고/처방전까지 가면 범위가 커짐
  • 초기에는 “보호자 공유/문서 발송/예약”에 집중

5. 상품 판매 구조

로얄캐닌 총판 연결은 강한 진입 포인트입니다. 다만 병원 연계와 커머스를 섞을 때는 “진료 데이터 기반 추천”과 “일반 쇼핑”의 경계를 명확히 해야 신뢰가 유지됩니다.

영역 필요 기능 기존 코드와 연결 우선순위
판매자 센터 상품 등록, 이미지, 가격, 재고, 옵션, 배송정책, 상세 페이지 작성 관리자 구조를 확장하거나 별도 /seller 라우트 생성 높음
구매자 쇼핑 상품 목록, 상세, 장바구니, 바로구매, 주문내역 기존 Toss 결제 API를 단건 결제 승인 후 연결 높음
정기배송 사료 주기별 자동결제, 배송일 변경, 일시중지 이미 빌링키 흐름이 있어 확장 가능 높음
병원 추천 상품 담당 수의사가 특정 상품/식이 관리 안내를 보호자에게 공유 병원 문서/메시지 기능과 연결 중간
정산 판매자별 매출, 수수료, 환불, 배송비, 정산 상태 운영자 관리자에 정산 메뉴 추가 중간
추천 판매 흐름: 처음에는 로얄캐닌 사료 중심으로 상품 수를 제한하고, “반려동물 프로필 → 나이/체중/질환 태그 → 추천 사료 → 정기배송” 흐름을 만들면 기존 기록 앱과 연결성이 높습니다.

6. 추가 데이터 설계 초안

현재 Supabase에는 profiles, pets, health_records, medications, record_files, subscriptions, payment_history 등이 있습니다. 여기에 병원/의사/공유/예약/문서/커머스 테이블을 추가하는 방향이 자연스럽습니다.

병원 연계

추가 테이블 후보

  • hospitals: 병원 프로필, 주소, 연락처, 진료시간
  • hospital_members: 병원 소속 의사/직원/관리자 권한
  • veterinarians: 수의사 프로필, 전문 분야, 예약 가능 여부
  • care_shares: 보호자-병원 기록 공유 동의와 만료일
  • appointments: 예약 요청/확정/취소/담당 수의사
  • emergency_calls: 응급 요청, 상태, 응답자, 콜백 기록
  • medical_documents: 진단서/검사결과/주의사항 문서
커머스

추가 테이블 후보

  • sellers: 판매자/총판 정보
  • products: 상품, 브랜드, 카테고리, 노출 상태
  • product_variants: 옵션, 가격, 재고, SKU
  • carts: 장바구니
  • orders: 주문, 결제, 배송, 환불 상태
  • order_items: 주문 상품 단위
  • recurring_deliveries: 정기배송 주기와 다음 결제일
  • seller_settlements: 판매자 정산
개인정보/의료 리스크: 병원 연계부터는 민감정보 처리에 가까워집니다. 공유 범위, 동의 이력, 열람 로그, 철회 기능, 파일 접근 권한, 관리자 접근 로그를 반드시 남겨야 합니다.

7. 추천 우선순위

지금 상태에서 가장 좋은 순서는 “기록 데이터의 병원 공유 → 병원 문서 발송 → 예약 → 커머스”입니다. 커머스를 먼저 크게 만들면 기존 앱의 핵심 가치와 분리될 수 있습니다.

1순위

병원/의사 계정과 보호자 공유 동의

병원 연계의 기초입니다. 이게 있어야 검사결과 공유, 예약, 응급 콜이 모두 안전하게 붙습니다.

2순위

의사용 웹 대시보드 MVP

환자 검색, 공유된 기록 보기, 문서 업로드/전송, 예약 확인만 먼저 만듭니다. 설치형 프로그램은 웹이 검증된 뒤 패키징합니다.

3순위

보호자 앱의 병원 탭 추가

담당 병원, 담당 수의사, 예약, 받은 문서, 공유 상태, 응급 콜을 한 화면에서 관리하게 합니다.

4순위

로얄캐닌 중심 구매/정기배송

상품 수를 제한하고 결제/배송/주문내역을 안정화합니다. Toss 단건 결제 심사 완료 후 바로구매를 붙입니다.

5순위

응급 콜과 병원 운영 자동화

병원 응답 가능 시간, 응급 요청 분류, 전화/채팅/알림 연동은 운영 부담이 커서 병원 MVP 이후가 좋습니다.

보호자 앱: 기록 + 공유 + 예약 + 구매 병원 웹: 환자 타임라인 + 문서 발송 + 예약 관리 운영자: 병원/판매자 승인 + 결제/정산 + 로그 판매자: 상품/재고/주문 관리
